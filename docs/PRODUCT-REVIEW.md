# 个人器件库 v1.1.0 · 产品评估与优化需求

> 评估对象：`PersonalDeviceManagement` v1.1.0（21 次提交 / 约 4,900 行源码 / 99 项测试）
> 评估视角：产品经理（功能完整性、用户体验、核心场景覆盖、商业化潜力、技术实现与产品目标匹配度）
> 评估方式：全量源码与文档阅读 + 本机实测复现（非仅文档走查）
> 评估日期：2026-11-07
> 配套文件：`docs/TODO.md`（可勾选执行清单）

## 0. 一页结论

**这是一个完成度远超"课程作业"的可运行产品原型，但离"能长期托付自己器件库存的工具"还差三个台阶。**

五大自定需求全部有真实可用的实现，安全链路（白名单→C 转义→生成扫描→本地守卫）达到工业级严谨度，虚拟器件盒让它无需硬件即可完整演示——这三点在同类学生作品中相当罕见。

但实测暴露了一个致命错位：**产品按 63 格设计，核心联动在第 14 个器件就断了**。

```
13 个映射 → sync 载荷 500 字节 → 连接成功
14 个映射 → sync 载荷 536 字节 → 超 512 字节上限 → 连接失败："命令超过协议长度限制"
```

默认布局是 7×9 = 63 格。也就是说，**设计容量的 78% 是不可用的**，而且失效点在"用户刚开始觉得这玩意儿有用"的那一刻。更糟的是，映射变更触发的自动同步异常被静默吞掉（`boxmap._notify_sync` 里的 `except: pass`），用户改完映射、实体盒毫无反应，也无任何提示。

| 维度 | 得分（1–5） | 一句话判断 |
|---|---|---|
| 功能完整性（对照五大自定需求） | **4.0** | 需求①~⑤ 全部落地，含虚拟盒全闭环 |
| 功能完整性（对照品类基准） | **2.5** | 缺 BOM 配单、盘点、库存流水、多盒、备份 |
| 核心场景覆盖 | **2.5** | "入库→映射→取料"成立；"找料/盘点/补货/换盒"断裂 |
| 用户体验 | **3.5** | 因果反馈、空态、错误文案用心；长任务无进度、无引导 |
| 商业化潜力 | **2.5** | 软硬一体护城河清晰；单盒 + 无 BOM + GPL 三重约束 |
| 技术实现 ↔ 产品目标匹配度 | **3.5** | 安全与本地化极佳；协议规模、NVS 指纹、单例模型拖后腿 |
| **综合** | **3.1 / 5** | 高完成度原型，欠账集中在「库存可信度」与「最后一公里」 |

**三条最高杠杆（做完这三件，产品性质就变了）：**

1. **修协议规模边界**（0.5 人日）—— 让 63 格真的能用。这是"能不能用"的问题。
2. **让库存可信**（流水 + 导入幂等 + 备份，约 5 人日）—— 让用户敢把真实库存托付给它。这是"敢不敢用"的问题。
3. **找料闭环**（搜索器件 → 点亮格位，约 1 人日）—— 把"管理库存"变成"3 秒找到东西"。这是"想不想用"的问题。

## 1. 评估口径（先说清楚我在评什么）

| 项目 | 说明 |
|---|---|
| 需求基准 | 项目自定的五大需求（①导入 ②联动 ③动态映射 ④生成代码 ⑤安全） |

| 实测手段 | `pytest` 全量运行（99 passed，10.07s）；构造 12~25 条映射二分复现联动阈值；核算 sync 载荷字节数 |
| 不在本次范围 | 代码风格与命名、具体实现选型优劣、性能微优化（属技术 review）；竞品功能复刻 |
| 数据说明 | 本文所有"用户""市场"判断均为基于产品形态的推演，**未做真实用户访谈**，标注为「推演」 |

> **一个必须先讲的方法论提醒**：99 项测试全绿，却漏掉了最致命的那个 bug。原因是测试用例只用 1~2 个映射验证链路通断，**从未验证"设计容量下的规模行为"**。这不是测试写得不好，是测试的"规模假设"没被写进验收标准。产品侧的教训：**任何"可配置上限"都必须有一条"上限处仍可用"的验收用例**。

## 2. 五维评估

### 2.1 功能完整性

#### 对照五大自定需求

| 需求 | 实现程度 | 证据 | 缺口 |
|---|---|---|---|
| ① 立创批量导入 + 手工维护 | ✅ 强 | 订单 xlsx/xls/csv 多文件、表头定位 + 全表正则兜底、C 编号两阶段预览导入、全字段 CSV 往返 | 订单文件导入**无预览**（直写库）；重复导入无幂等 |
| ② 与器件盒联动 | ⚠️ 部分 | 串口 JSON + 连接即 sync + 取退料双向改库存 + 虚拟盒 | **≥14 映射连接失败**；无断线重连；无心跳超时 |
| ③ 动态配置映射 | ✅ 强 | 1×1~16×24 / ≤256 格、4 组预设、越界映射移除并报告 | **只支持一个盒**（`box_config id=1` 单行） |
| ④ 配置即生成固件 | ✅ 强 | 配置层/代码层分离、模板复制 + 渲染 + 扫描 + 落盘、`.pdl_firmware` 防覆盖 | 仍需 VSCode+PlatformIO 五步外部操作，无编译/烧录校验 |
| ⑤ 软件层↔代码层安全 | ✅ 优秀 | 五道防线、Unicode 双向控制符过滤（防 CVE-2021-42574）、CSP、防 DNS rebinding、防 drive-by CSRF、随机令牌保护生命周期端点 | —— |

#### 对照品类基准（这才是"个人器件库"该有的完整样子）

| 能力 | 状态 | 说明 |
|---|---|---|
| 器件台账（增删改查/搜索/分页） | ✅ | 搜索覆盖名称/C编号/描述/封装/品牌，转义 `%_` 防注入 |
| 分类与标签 | ⚠️ | 有 `category` 字段但**无分类树、无筛选入口**，实际沦为自由文本 |
| 入库（采购到货） | ⚠️ | 只有"导入即入库"，无采购单、无到货核对、无成本核算 |
| 出库/消耗 | ⚠️ | 只有"取料 −1"，无项目归属、无用途记录 |
| 库存流水（审计） | ❌ | **完全没有**。`qty` 是唯一真相，改了就改了 |
| 盘点 | ❌ | 完全没有 |
| 低库存预警 | ⚠️ | 仅前端硬编码 `qty<=5` 变红，无阈值配置、无预警清单、无筛选 |
| BOM 配单 / 缺料检查 | ❌ | 完全没有（这是本品类最高频刚需） |
| 多仓/多盒/库位 | ❌ | 单盒单例 |
| 价格与资产 | ⚠️ | 有价格刷新，但 USD（接口）与人民币（手填）混排，无汇率、无库存总值 |
| 标签打印 | ❌ | 实体盒贴标是落地必需，完全缺失 |
| 备份/恢复 | ⚠️ | 仅 CSV 导出（**不含映射与硬件配置**），无恢复、无自动备份 |

### 2.2 核心场景覆盖（场景地图）

按"一个电子专业学生的真实一学期"走一遍：

| # | 场景 | 覆盖 | 判断 |
|---|---|---|---|
| 1 | **入库**：下单、到货、录进系统 | ⚠️ | 能导入，但重导入即翻倍，且无到货核对、无单价成本 |
| 2 | **整理**：把器件放进盒子并告诉软件放在哪 | ✅ | 尺寸/预设/一键排布都顺手；但**只有分类字段、没有"按分类分区排布"**，实际放盒仍靠脑子 |
| 3 | **找料**：我要那颗 100nF 0603，在哪一格 | ❌ | **断裂**。软件内无法"输入器件名 → 格位亮灯"，只能人肉逐格找；器件列表也不显示"在哪个格位" |
| 4 | **取用**：从盒里拿走 | ⚠️ | 按键取料很酷，但**第 14 个器件起连接不上** |
| 5 | **退料**：放回去 | ⚠️ | 有 +1，但无"放错格位"校验；换映射重新烧录后库存会错位（见 D-06） |
| 6 | **盘点**：期末对齐实物与账面 | ❌ | 完全没有。63 格逐格核对只能靠手工改数字 |
| 7 | **补货**：快用完了要买 | ❌ | 只有变红的视觉提示，无阈值、无清单、无导出 |
| 8 | **扩盒**：买了第二个盒子 | ❌ | 单盒架构，无法管理 |
| 9 | **换机/重装**：数据不能丢 | ❌ | 只有 CSV，映射与硬件配置全丢；无备份、无恢复 |

**结论：9 个核心场景，2 个成立、3 个半残、4 个完全断裂。** 断裂的 4 个（找料、盘点、补货、备份）恰好是"从玩具变成工具"的分水岭。

### 2.3 用户体验

**做得好的（应当保留的资产）：**

| 亮点 | 出处 | 为什么好 |
|---|---|---|
| 完成态 ≥1.5s 驻留 + 格位闪烁回执 | `app.js` `flashCell(hold=1600)` | 做了"操作→反馈"的因果可感知，多数同类工具没有 |
| 虚拟器件盒 | `serial_bridge.VirtualBox` | 无硬件可完整演示，既是体验设计也是销售工具 |
| 同一条处理路径 | `_on_raw_event` / `_on_raw_line` 汇入 `_handle_event` | 虚拟与真实行为一致，演示可信 |
| 错误文案面向用户 | `"未安装 pyserial:pip install pyserial"` | 告诉用户怎么办，而非抛栈 |
| 两阶段导入（预览-编辑-确认） | `preview_codes` / `save_preview` | 已有器件锁定人工字段、标注"已存在·合并"，防误覆盖 |
| 越界映射移除后明确报告 | `update_config` 返回 `removed_mappings` | 破坏性操作有交代 |

**主要摩擦点（按用户痛感排序）：**

| # | 摩擦 | 现象 | 根因 |
|---|---|---|---|
| 1 | 长任务无进度、无耗时预期 | 价格刷新 100 件 = 100×0.35s ≈ 35s+，全程只有一个禁用按钮 | 同步阻塞请求，无任务模型 |
| 2 | 错误只在 toast 飘一下 | GPIO 冲突提示 `引脚冲突:GPIO48 同时分配给了 led_pin 与 btn_up`（用字段名） | 无字段级内联校验 |
| 3 | 破坏性操作不可逆 | 清空映射 / 一键排布直接 `DELETE FROM mappings`，误点即全丢 | 无快照、无撤销、无软删除 |
| 4 | 首启空白无引导 | 三个页签、一堆空表格，不知道第一步该干什么 | 无 onboarding、无示例数据一键载入 |
| 5 | 半成品功能暴露 | `/api/import/logs` 有接口，前端从未调用 | 接口先行、界面遗忘 |
| 6 | 点亮状态跨格位错乱 | `state.cellLit` 是全局 toggle，切换格位不复位 | 状态未绑定实体 |
| 7 | 空态表格列宽错位 | `colspan="9"`，实际 10 列 | 细节 |
| 8 | 器件与格位单向可见 | 列表看不到"在哪个格位"，格位也回不到器件详情 | 缺反向索引的 UI |
| 9 | 排序能力"有后端无前端" | API 支持 `sort=name_asc/qty_desc/code_asc`，UI 无入口 | 半成品 |
| 10 | 上传文件永久堆积 | `uploads/` 落盘后从不清理 | 无 TTL |
| 11 | 事件延迟 1.2s | 轮询 `/serial/events`，后台页面也轮询 | 无推送、无可见性暂停 |
| 12 | 无键盘/无障碍 | 全部鼠标操作，弹窗无焦点管理 | 未纳入验收 |

### 2.4 商业化潜力

**用户分层与规模（推演）：**

| 层 | 画像 | 规模（推演） | 付费意愿 | 当前产品适配度 |
|---|---|---|---|---|
| 核心 | 电子类专业学生/毕设/竞赛队 | 国内每年数十万 | 低（愿为硬件付费，不愿为软件订阅） | 高（单盒够用） |
| 扩展 | 创客/独立开发者/小团队 | 数万 | 中 | 低（缺多盒/BOM/共享） |
| 机构 | 高校实验室/实训室/中小学创客空间 | 数千 | 高（按套采购） | 极低（缺批量部署与统一管理） |

**价值主张（一句话）**：让"实体盒子里的东西"和"软件里的账"永远一致，并且 3 秒内找到任意一颗器件。

**护城河判断**：真正的壁垒不是器件库（InvenTree、Excel、飞书表格都能做），而是 **"映射即固件"**——用户改完格位分配，软件直接吐出可烧录的固件，硬件界面自动适配。纯软件产品复制不了这条链路，纯硬件产品也做不了这层抽象。**这是唯一值得围绕它做商业化的点。**

**付费点设计（按毛利排序）：**

| 变现方式 | 逻辑 | 可行性 |
|---|---|---|
| 硬件套件（盒体 + 灯板 + 主控 + 亚克力格栅） | 软件的物理载体，客单价 150~400 元 | 高（最现实） |
| Pro 授权（多盒 / BOM / 盘点 / 标签 / OTA / 云备份） | 从"个人一个盒"升级到"一柜子盒" | 中 |
| 教育版（批量烧录 + 模板化映射 + 统一资产表） | 实验室按套采购，含实施 | 中（需销售能力） |
| 定制固件服务 | 特殊盒型/特殊协议 | 低 |

**四点商业化障碍（必须正视）：**

1. **单盒架构**——只有一个盒子的人不需要付费，有两个盒子的人用不了。
2. **无 BOM 配单**——用户最痛的时刻是"照着 BOM 备料发现缺三样"，这个场景产品完全不接。
3. **烧录仍需 PlatformIO**——从"生成成功"到"灯亮起来"有 5 个外部步骤，这是转化漏斗上最大的漏水口。**一键烧录是能不能卖套件的前置条件。**
4. **GPL-3.0 许可**——当前许可要求衍生作品开源。若计划做闭源 Pro 或商业套件配套闭源软件，**必须在写第一行 Pro 代码之前**决策：维持 GPL + 纯套件变现 / 双许可 / 更换许可（需所有贡献者同意）。

**诚实结论**：这是一个 **TAM 有限、但护城河真实**的品类。不适合按 SaaS 估值，适合"开源核心建立影响力 + 硬件套件变现 + Pro 增值"的组合。对保研/作品集而言，它的价值不在商业规模，而在**"软硬全栈闭环 + 安全工程 + 产品化思考"的完整叙事**——这一点它已经做得很好。

### 2.5 技术实现与产品目标的匹配度

| 产品目标（原文） | 实现 | 匹配度 | 差距 |
|---|---|---|---|
| "全程无需手写或修改任何代码" | 配置层/代码层分离，用户永不碰 C | **高** | 不写代码 ≠ 无门槛，仍需装 VSCode+PlatformIO、选板、点 Upload |
| "与自定义器件盒联动" | 换行 JSON 协议 + 虚拟盒 | **中** | 512B 单行上限在 14 格失效；无重连；无心跳 |
| "动态配置映射适配不同盒型" | 尺寸/预设/越界报告 | **中高** | 单盒；`cell` 是 `row*cols+col` 派生量，改列数后格位号整体漂移，用户与固件对不上 |
| "库存准确" | `qty` 单字段 + 固件 NVS | **低** | 无流水、无幂等、无盘点；NVS 按 cell 号存，换映射即错位 |
| "软件层与代码层安全管理" | 五道防线 | **优秀** | 无短板，是全项目最扎实的部分 |

**结构性技术债（影响后续所有迭代，建议尽早决策）：**

| # | 技术债 | 影响 | 处理时机 |
|---|---|---|---|
| 1 | 单例模型（`box_config id=1`、单 `SerialBridge`、单 COM 口） | 多盒 = 数据模型 + 连接管理 + 固件寻址三处重构 | **v2.0 前必须决策**，越晚越贵 |
| 2 | 文本 JSON 单行协议 + 512B 上限 | 规模天花板 14 格，扩容只能改协议 | 立即（P0） |
| 3 | 无任务队列，长任务同步阻塞 | 价格/导入体验差，易超时 | P1 |
| 4 | 轮询替代推送（1.2s） | 事件延迟、无谓请求 | P1 |
| 5 | 无 schema 版本（未用 `PRAGMA user_version`） | 迁移只支持加列，未来改表结构风险高 | P1（随手补） |
| 6 | 无观测性（无运行日志文件、无错误上报） | 用户报"连不上"时无法定位 | P2 |
| 7 | 状态派生而非持久（`cell` 编号） | 改列数后格位号漂移 | P2 |

## 3. 缺陷清单（按严重度）

> **P0 = 阻断核心闭环，或造成不可逆数据损失**；P1 = 显著影响可用性/信任；P2 = 打磨项。
> 证据列给出 `文件:行`，可直接定位。

### P0 · 必须先修

| ID | 现象 | 证据 | 影响 | 根因 |
|---|---|---|---|---|
| **D-01** | **映射 ≥14 个时连接器件盒失败**，提示"命令超过协议长度限制"；63 格设计容量实际只能用 13 格 | `serial_bridge.py:21`（`MAX_LINE=512`）、`:243-244`（超限抛错）、`:199-203`（`connect()` 内直接调 `push_sync()` 无保护）；`protocol.cpp:71,159`（固件同样 512B 丢弃） | **核心功能在真实规模下不可用**；演示到第 14 个器件即崩 | 全量映射打成一条 JSON 单行，无分批/分帧 |
| **D-02** | **重复导入同一订单 → 库存翻倍** | `importer.py:281-294`（`qty = qty + ?` 累加，无订单号/批次幂等键） | 库存失真，用户不再信任任何数字 | 导入模型是"事件"而非"幂等同步"，无批次身份 |
| **D-03** | **无库存流水，任何增减不可追溯、不可撤销** | `db.py:19-74`（schema 无 moves 表）；`devices.py:192-204`（`adjust_qty` 只 `UPDATE qty`） | 误操作无法定位与回滚；无法回答"这批电阻什么时候少的"；盘点无依据 | `qty` 被当作唯一真相，缺少事件源 |
| **D-04** | **破坏性操作不可逆**：清空映射 / 一键排布 / 批量删除 | `boxmap.py:187-193`（`DELETE FROM mappings`）、`:196-210`（先删全表再重排）；`devices.py:183-189`（硬删除） | 一次误点丢失全盒布局或整批器件 | 无快照、无撤销、无软删除 |
| **D-05** | **无完整备份/恢复**：仅 `devices.csv`，不含映射、硬件配置、固件指纹 | `api.py:246-251`（仅导出 devices 表） | 换机/重装/磁盘故障 = 数据全丢，且无任何提示 | 单机本地存储，但未提供与之匹配的数据保护 |

## 5. 明确不做的事（Scope 控制）

范围蔓延是这类个人项目最大的死因。以下四项主动列为 **Won't（本期）**，并记录理由：

| 不做 | 理由 | 重新评估条件 |
|---|---|---|
| 云同步 / 多端同步 | 与"本地优先、隐私自持"的核心定位冲突；引入账号、运维、合规成本 | 出现明确的团队协作付费需求 |
| 移动 App / 小程序 | 找料场景用"格位二维码 + 手机扫码"更轻，不需要 App | 若做扫码找料仍不满足，再议 |
| 多用户与权限体系 | 单机个人工具，权限无意义；教育版才需要 | 教育版立项时 |
| AI 推荐/智能补货 | 数据量不足以支撑，且容易做成噱头 | 积累 ≥6 个月真实消耗流水后 |
